## 二、方法口径与实验发现

- **Header / SPDX Keyword Scanner**：仅检测文件内显式 SPDX/许可证名/版权声明/常见许可套话；不依赖语料库，但对无文件头源码及截取片段(partial)漏检严重，且无法归因无头抄袭。（总耗时 0.04s）
- **Verbatim Line-Hash Matcher**：按非空归一化行构建 k=5 连续行块哈希倒排索引（1,717 文档），匹配覆盖率 ≥ 0.25 判定命中。（总耗时 2.31s）
- **Raw Token Jaccard (L1-only)**：仅使用原始代码 token 6-gram（L1 字面层，无 AST 别名/角色/结构边归一化，无 IDF 与判定模型），经 LSH 召回后以 Jaccard ≥ 0.30 判定命中。（总耗时 57.65s）
- **CodeGuard (4-Layer + 12-Dim Judge)**：完整生产管线：L2/L3/L4 多层 MinHash+LSH 召回 + 4 层精确验证(含 L1 逐字连续运行) + IDF 加权 + 12 维逻辑回归判定 + 佐证门槛(corroborated)；未达佐证门槛的弱命中仅作 S0/S2 观察提示、不触发门禁阻断。（总耗时 33.24s）

### 关键结论

1. **传统头部/SPDX 扫描（36.1% 召回）**：AI 生成或开发者复制片段常剥离文件头与 SPDX 注释，`partial` 片段截取场景下召回率骤降至 **8.3%**，且仅能识别显式声明、无法归因缺失许可证声明的源码复用。
2. **逐行哈希匹配（71.5% 召回）**：保留空白归一化后能覆盖原文与纯缩进重排，但注释/文档串注入（`comment_inject` 79.2%）、变量重命名（`rename` 41.7%）与复合改写（`compound` 12.5%）会破坏连续行块哈希，复合改写召回仅 12.5%。
3. **纯字面 Token Jaccard（L1-only，81.9% 召回）**：去除了空白和注释干扰后抗格式化/注释能力提升，但缺少 AST 角色抽象（L3）与结构边（L4）导致变量改名后 6-gram 碎片化，`rename` 仅 **62.5%**、`compound` 仅 **58.3%**。
4. **CodeGuard 四层指纹 + 12 维判定模型（95.8% 召回，F1=0.979，FPR=0.0%）**：在 1,717 文档全量语料检索下，对 `identity` / `rename` / `reformat` / `comment_inject` / `compound` 均保持 **100.0%** 检出与真源归因，同时通过佐证门槛将 9 个独立自研负例的误阻断控制在 **0/9**（佐证前弱观察命中 2 例，均未触发阻断）。在 `partial` 场景达到 **75.0%**（18/24 达佐证门槛，19/24 检出）。
