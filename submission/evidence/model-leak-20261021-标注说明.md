# 47 条真实模型正例 · 双人盲标说明

> 用途：给“实现完成度与可验证效果”和“AI 与开源融合”两项提供**真人独立标注**证据。
> 底线：两名标注人各自看自己的对照包、各自填自己的 CSV，不讨论、不抄论文标签、不把空值当 A。
> 赛事规则明确禁止伪造佐证；如果最终只做单人标注或直接采用论文标签，报告必须如实写
> “单人标注”或“采用 LiCoEval 论文标签”，**不得写成“双人独立标注”**。

## 0. 队友不会用 CSV？用 annotate.html

如果队友不熟悉 Excel/CSV，队长运行：

```bash
python scripts/make_annotation_kit.py
```

生成 `scratch/CodeGuard-annotation-kit.zip`。队友解压后双击 `start.bat`（或把 `annotate.html` 拖进 Edge/Chrome），选择“标注人1/2”，逐条点 A/B/C，完成后点“导出我的 CSV”。

工具会自动：
- 展示左右对照、相同片段高亮、CodeGuard 指标；
- 保存进度，并导出与 `merge_annotations.py` 同格式的 CSV；
- 在“标注汇总”页计算一致率、Cohen's κ、分歧清单和报告句子；
- 在“试用汇总”页把两份试用原始表整理成汇总 Markdown。

工具**不会**替队友填 A/B/C；那会让“双人独立标注”变成机器标注。队友只需要点按钮和写一句话理由。

## 2. 标注口径（A/B/C）

先记住一句话：**论文说这 47 条是 striking-similar，不等于你也要判 A；你判的是“这段相似是否构成实质复现”。**

- **A = 实质逐字复现（可判定为许可污染）**
  - 回答里有连续、非平凡的一段实现与原文对应，通常 **≥20 个逐字 token**；
  - 或 **≥10 个逐字 token 且覆盖率较高**，且被复制的是有表达性的函数体、算法步骤、数据结构操作；
  - 改名、改格式、插注释不影响 A；看的是去掉表面差异后的实现是否仍然一一对应。
- **B = 惯用写法 / 公共片段巧合**
  - 只共享 imports、`argparse`、异常处理、常量表、短签名、文档字符串、常见数学/IO 写法；
  - 或只是“同一个 API 的标准用法”“同一个算法的通用骨架”，换个人写也会长这样；
  - 没有实质表达被复制，不构成许可污染。
- **C = 无法判断**
  - 片段太短、原文本身过于通用、回答是残片、边界需要版权法判断；
  - 拿不准就填 C，并在 `note` 写清楚卡在哪；C 会交第三人复核，不丢人。

### 三个容易判错的边界

1. **跨项目副本**：CodeGuard 可能命中同一段上游代码的另一个仓库（CSV 的 `codeguard_attributed=否`）。
   你仍然拿 GPT-4o 回答与**论文配对原文**比；如果回答确实复制了这段代码，判 A，并在 `note`
   写“命中为同源副本，非论文预期项目”。不要因为归属项目不同就判 B。
2. **注释/文档字符串**：如果回答只复制了注释、docstring 或版权头，没有复制实现，判 B；
   如果注释 + 实现一起成段复制，按实现部分判 A。
3. **短片段**：只有 1–2 行、且是通用表达式（如 `return a + b`），判 B 或 C；
   不要因为 CodeGuard 给了 S1/S2 就判 A。

## 3. 流程（每人约 60–90 分钟）

1. 打开自己的对照包：双击 `.codeguard/annotation/packet-annotatorN.html`。
2. 从第 1 条开始，按顺序看：
   - 顶部：论文配对项目、许可、BLEU/Jaccard、CodeGuard 风险/逐字/覆盖率；
   - 左侧：GPT-4o 回答；右侧：论文配对原文；黄色高亮只是定位；
   - 展开“CodeGuard 实际命中”只看系统读数，不把它当结论。
3. 在**自己的 CSV** 里填：
   - `label`：A / B / C（只填这三个字母）；
   - `note`：B/C 必填一句理由；A 如果跨项目或特别短，也写一句；
   - `date`：填写日期；`annotator` 可改成你的昵称/代号。
4. 47 行填完后，检查没有空 `label`。不要改 `expected_*`、`paper_*`、`codeguard_*` 这些客观列。
5. 两份都填完后，由队长运行：

```bash
python scripts/merge_annotations.py
```

输出 `submission/evidence/model-leak-20261021-标注汇总.md`，里面有：
一致数/47、Cohen's κ、分歧清单、最终 A 数，以及一段可直接写进报告的句子。

6. 如果一致率或 κ 不理想：先看分歧样本，再讨论口径（不是改答案），必要时重标；
   仍不一致的，交第三人复核，把复核结论填进汇总表的“复核结论”列。
   注意 κ 对分布偏斜敏感：如果一方几乎全判 A，即使一致率 95%+，κ 也可能接近 0；
   报告时同时写一致率和 κ，不要把 κ=0 误读为双方完全不一致。
7. 如果时间不够：**不要伪造**。如实写“单人标注”或“采用论文标签”，并在报告里说明局限；
   这比一个假的“双人 47/47”安全得多。

## 4. 结果怎么写进报告

- 只有在两份 CSV 填满、`merge_annotations.py` 成功生成汇总后，才可以写“双人独立标注”。
- 建议写法（数字以汇总为准）：
  > 两名成员对 LiCoEval 的 47 条 GPT-4o 真实输出独立标注：一致 43/47（91.5%），Cohen's κ=0.82；
  > 标注人1 判 A 45 / B 2 / C 0，标注人2 判 A 44 / B 2 / C 1；4 条分歧经第三人复核后，
  > 最终独立确认 A 46 条。论文把这 47 条都标为 striking-similar；本表的 A 是团队独立确认，
  > B/C 是不确认或拿不准，不能写成“47/47 确认为复现”。若一方几乎全 A 导致 κ 偏低，
  > 同时报告一致率和 κ，并说明分布偏斜，不要只挑一个数字。
- 如果最终 A 数少于 47，**不要**把“47/47 命中”改写成“47/47 确认为复现”；
  命中是检测器读数，A 是人工判断，两件事。
- 同时更新 `submission/evidence/README.md` 的标注行，以及报告 §5.3 的“后续需要完成”段落
  （把“待双人标注”改成实际结果）。

## 5. 许可与隐私

- 对照包是 LiCoEval 的本地评测副本，AGPL-3.0-or-later；只用于本次评审证据，不再分发。
- 不要把对照包、原文截图、模型输出上传到公开仓库/网盘/PPT/视频。
- CSV 不含源码，只有样本 ID、项目名、许可、指标、A/B/C 和一句话理由；可以作为佐证提交。
- 标注人姓名可用昵称/代号；不要在 CSV 里写学校、学院、教师姓名。

## 6. 快速检查

```bash
python scripts/make_annotation_packet.py          # 重新生成对照包与空白 CSV
python scripts/merge_annotations.py --allow-blank # 只检查模板，不生成完成结论

```

如果 `merge_annotations.py` 报“标注未完成”，说明还有空 `label`；它不会把空值当作 A。
